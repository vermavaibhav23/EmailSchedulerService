# Railway: deploy in dependency order

## 1. Create project and infrastructure

Create a Railway project named `EmailSchedulerService`. Add PostgreSQL and Redis database services with persistent volumes. Redis must use `redis-server --appendonly yes --appendfsync always --maxmemory-policy noeviction`, with its data volume mounted at `/data`. Preserve the Redis template's password protection when changing its command: include `--requirepass "$REDIS_PASSWORD"` through a shell start command using the `REDIS_PASSWORD` variable generated by Railway. Do not replace an authenticated template command with an unauthenticated command.

Add Elasticsearch as a Docker-image service using `elastic/elasticsearch:8.17.0`, a volume at `/usr/share/elasticsearch/data`, and variables `discovery.type=single-node`, `ES_JAVA_OPTS=-Xms512m -Xmx512m`, `xpack.security.enabled=true`, `xpack.security.http.ssl.enabled=false`, `xpack.security.transport.ssl.enabled=false`, and a randomly generated `ELASTIC_PASSWORD`. Expose it only on Railway's private network, never with a public domain or TCP proxy. Set matching `ELASTICSEARCH_PASSWORD` on the API and worker. HTTP remains private and authenticated; for public/external Elasticsearch use authenticated HTTPS and set `ELASTICSEARCH_API_KEY` instead. Set `ELASTICSEARCH_URL=http://elasticsearch.railway.internal:9200` using the actual service's private domain. Single-node Elasticsearch requires meaningful RAM; review the Railway account's plan and resource limits before deploying.

Railway volumes are mounted as root. For this Elasticsearch image set `RAILWAY_RUN_UID=0` and the following custom start command; it fixes volume ownership then drops to the Elasticsearch service user before boot:

```sh
/bin/bash -c 'chown -R 1000:0 /usr/share/elasticsearch/data && exec su -s /bin/bash elasticsearch -c "export PATH=/usr/share/elasticsearch/bin:/usr/local/bin:/usr/bin:/bin; exec /usr/local/bin/docker-entrypoint.sh eswrapper"'
```

## 2. Add API and BullMQ worker

Create two services from `vermavaibhav23/EmailSchedulerService`. Both use repository root and the Dockerfile. In Railway Settings, select Dockerfile as builder. Set API start command `npm start` and worker start command `npm run worker`; set pre-deploy command `npm run migrate` on both. Set `/health/live` as the API health check; the worker has no HTTP health check. The legacy TOML files are included as reference only: this Railway account currently disallows enabling legacy Config as Code for new services. The API serves the React UI as well. No extra static hosting or BullMQ instance is required.

For both services set matching variables:

| Variable                                | Value                                                                 |
| --------------------------------------- | --------------------------------------------------------------------- |
| DATABASE_URL                            | `${{Postgres.DATABASE_URL}}` using the actual PostgreSQL service name |
| REDIS_URL                               | `${{Redis.REDIS_URL}}` using the actual Redis service name            |
| ELASTICSEARCH_URL                       | Elasticsearch private URL above                                       |
| ELASTICSEARCH_PASSWORD | `${{elasticsearch.ELASTIC_PASSWORD}}` |
| SESSION_SECRET                          | Stable random 32+ character secret                                    |
| ENCRYPTION_KEY                          | Stable random 32-byte hexadecimal key                                 |
| APP_URL                                 | API's generated public HTTPS domain                                   |
| GOOGLE_CLIENT_ID / GOOGLE_CLIENT_SECRET | Google OAuth app credentials                                          |
| SLACK_CLIENT_ID / SLACK_CLIENT_SECRET   | Slack OAuth app credentials                                           |
| WORKER_CONCURRENCY                      | `5`                                                                   |
| MIN_SEND_DELAY_MS                       | `2000`                                                                |
| MAX_EMAILS_PER_HOUR_PER_SENDER          | `200`                                                                 |
| ADMIN_EMAILS                            | Your Google login email, comma separated for multiple admins          |

`NODE_ENV=production` is set by Docker. Set `PORT=3000` on the API and use target port 3000 for its public domain; the API listens on all interfaces. Both pre-deploy commands run the migration safely under its DB lock. Set desired replicas; start with one worker, then scale once verified. Multiple API replicas share Redis sessions; multiple workers share Redis limits and DB claims.

Generate a public domain only for the API. The worker and infrastructure remain private. Add the exact public-domain callback URLs in both Google and Slack app settings:

- `https://<api-domain>/auth/google/callback`
- `https://<api-domain>/integrations/slack/callback`

## 3. Verify integrations before UI acceptance

Check each service's deployment status and logs. `/health/live` returns 200 as soon as the API serves; `/health/ready` must return 200 after DB, Redis, Elasticsearch and worker connect. Sign in using Google, provision an Ethereal sender, connect Slack, and schedule a small batch. Use the live verification checklist. Confirm persistent volumes and backups before restart testing.
